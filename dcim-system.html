Case study — data-centre infrastructure monitoring · built for a bank

Your data centre already
has monitoring. Five of them.

This is DCIM — a data-centre infrastructure monitoring system built for Dhaka Bank. Their facility ran on five vendors’ boxes: the transfer switches, the UPS wall, the precision coolers, the rack PDUs, the environment sensors — each with its own console, its own login, and its own licence renewal. DCIM folds them into one screen the bank owns outright. Scroll, and you’ll walk the whole facility on it.

onboarding cost

Each vendor console used its own words for the same idea — “on line”, “normal”, “bypass”, “eco”. A facilities engineer needed a week of shadowing before an alarm meant the same thing to them as to the shift lead.

  • Vendor terms for “fine”On Line · Normal · Running · OK · Healthy

The brief that came out of it: a monitoring product the bank owns, that reads the same across every device class, with the vendor in the same city. Everything after this is that brief, working.

The home screen

One screen that answers the only question.

The overview leads with a verdict for the whole facility, then a real floor plan you can read like a room, then the fleet broken down by device class. Five vendor systems, one layout — and every number is a link back to the box it came from.

  1. Facility verdict first — total power draw, active alarms, fleet uptime, PUE and cooling load sit across the top before you read a single gauge.
  2. The floor plan is real — server room, power room, network room, ISP room, drawn to layout, each labelled with its device count and its worst state.
  3. Fleet by class — ATS, Rack PDU, NetBotz, PAC, UPS — totals, how many are online, how many in alarm, and the one metric that matters for each.
  4. Nothing is a dead end — tap a room, a device type, an alarm count or a needs-attention row and you land on that exact box.

Cooling & environment

The room that isn’t allowed to get hot.

Power keeps the racks on; cooling keeps them alive. The environment view leads with the standard the auditors care about — ASHRAE A1 — then the numbers that predict trouble before a fan ever spins up: ΔT across the aisle, dew point, hotspot count, airflow balance, and a water-leak rope that’s either silent or screaming.

  1. The verdict is the standard — “ASHRAE A1 · Compliant” is the headline; the raw °C is secondary.
  2. Leading indicators, not trailing ones — dew point and ΔT move before a rack inlet does. Watch those and you get warning, not history.
  3. Hotspots are counted, not hunted — “0 hotspots · clear” is a number you can trust at a glance; a non-zero one links straight to the rack.
  4. Water leak is binary — “No leak” or a red rope. Nothing in between, nothing to interpret.

Why a first-timer can read it

Five device classes. One page shape.

This is the answer to “too complex to understand”. Whatever you open — a transfer switch, a UPS, a cooler, a rack PDU, an environment monitor — you get the same three tabs in the same order: Overview, Alarms / Events / Log, Report & Export. Learn one device page and you’ve learned all of them. Pick a class:

  • Transfer history in the event log, timestamped.
  • Per-bank overload thresholds, reset to default in one tap.

Alerts

One alarm log for 638 units.

Every event from every device class lands in one log, with one severity scale: critical, warning, info, system. Filter by device class, then drill into individual sensors — temperature on Rack A1, voltage on PDU-12 — without leaving the page. Response time and acknowledgement rate are measured, because the auditors ask.

  1. One scale, everywhere — the same four severities on the tile, the row, the device page and the export.
  2. Filter down to a sensor — device class → sensor category → the exact probe, all in the same panel.
  3. The clock is running — acknowledged vs. pending, and average response time, sit next to the log.
  4. Audit log is the same log — config changes, self-tests and backups are events too, in one chronological history.

Reports & compliance

Audit-ready by Monday, not by all-nighter.

A bank’s data centre has to produce energy usage, PUE, uptime, alarm history and maintenance records on demand. DCIM has one report library across every device class, six types out of the box, and a scheduler so the recurring ones file themselves and email the recipients.

One library, every device class

Environmental trends, power consumption with PUE, alarm history with root cause, performance analytics, uptime & availability, maintenance log — each with its own format (PDF · CSV · XLSX) and period.

  • Scheduled auto-reports — daily / weekly / monthly / quarterly, delivered to a recipient list, with last-sent and next-run visible and a “Run now” on every row.
  • Delivery is tracked — delivered vs. failed, and a success rate, so a missed compliance report is caught before the auditor catches it.
  • Same Report & Export tab on every device — the fleet report and the single-ATS report come out of the same flow.
